## 0. 文件定位與閱讀方式

本文件定義 Awoo 狼人殺的目標軟體架構、模組責任、資料所有權、遊戲階段、模組介面、測試要求與漸進式遷移原則。它是後續工程設計與程式修改的共同依據，不是目前程式已全部符合的聲明。

本文件區分三種資訊：

- **現況（Current）：** 可在目前 main 分支程式碼、文件或測試中找到的實作。
- **規格（MUST / SHOULD）：** 後續新增或重構時必須遵守的目標行為。
- **規劃（Future）：** 尚未實作的多人連線、伺服器權威狀態或其他平台能力。

不得把規劃項目描述為已完成，也不得只因單元測試通過就宣稱整局流程已通過瀏覽器驗收。

### 0.1 規範用語

- **MUST / 必須：** 不符合即視為違反架構規格。
- **MUST NOT / 不得：** 明確禁止的設計或操作。
- **SHOULD / 建議：** 除非有書面理由，否則應遵守。
- **MAY / 可以：** 允許採用，但非強制。
- **模組契約（Module Contract）：** 定義模組責任、輸入、輸出、可讀寫資料、事件及錯誤的明確邊界。

### 0.2 文件與程式的優先關係

1. 本規格定義目標架構；已確認的遊戲玩法需求定義玩家可觀察到的正確行為。
2. 目前程式碼只代表現況，不會因為已存在就自動成為正確規格。
3. 若現況與已確認需求衝突，必須先記錄差異、提出修正方案與回歸測試，再修改程式。
4. 若規格彼此矛盾或缺少必要房規，不得自行猜測；應列為待決議事項。
5. 修改本規格或遊戲規則時，應同步更新相關文件、測試與 CHANGELOG.md。

# 1. 專案目標與架構原則

## 1.1 專案目標

Awoo 是以瀏覽器為主要使用環境的狼人殺遊戲。系統包含角色、陣營、夜間行動、警長競選、天亮公告、死亡技能、白天發言、公投、遺言、上帝主持、角色圖鑑、影音及未來多人房間。

架構必須支援：

- 新增角色與技能時，不需要重寫整個回合流程。
- 新增房規時，不把規則散落在 UI 事件處理器。
- 修改一個階段時，不破壞其他階段的既有行為。
- 讓同一套遊戲規則可由測試模式、正式本機模式及未來多人模式使用。
- 清楚區分已實作、僅有角色資料、流程佔位及尚未驗收的功能。
- 透過可重現的自動化測試及人工驗收，保護既有功能。

## 1.2 架構型態

**目標採用模組化單體（Modular Monolith），不是微服務架構。**

目前產品是本機瀏覽器原型；在沒有真正多人伺服器的階段，不應為了形式而拆成多個網路服務。模組化應先落實在程式碼內，保留未來把權威遊戲核心移至伺服器的可能性。

## 1.3 核心原則

1. **單一狀態來源：** 同一個遊戲事實只能有一個權威來源。
2. **明確資料所有權：** 每個狀態欄位必須有唯一的主要管理模組。
3. **規則與畫面分離：** UI 不得自行實作角色技能、勝負判斷或階段規則。
4. **流程與口白分離：** 流程協調器決定下一階段；上帝主持模組只負責播報、等待及回報播放狀態。
5. **命令先驗證：** 玩家操作先經過命令／規則驗證，合法後才改變遊戲狀態。
6. **結果可追溯：** 夜間死亡、死亡技能、投票與警徽處理都必須留下可核對的結果。
7. **隱私先於顯示便利：** 私密資訊必須經過可見性政策，不能因為共用控制面板或公告欄而洩漏。
8. **漸進式重構：** 一次只遷移一個責任範圍；每次遷移都必須維持既有行為並通過回歸測試。

# 2. 整體架構與依賴方向

## 2.1 六個架構領域

| 領域 | 核心責任 | 主要內容 |
|---|---|---|
| 01. Game Core | 管理遊戲狀態、合法階段與命令入口 | Game State、Phase Machine、Command Handler、Event Bus |
| 02. Role System | 描述角色並定義可執行能力 | Role Registry、Role Metadata、Ability、Action Validator |
| 03. Game Phases | 執行各遊戲階段的流程 | Night、Sheriff Election、Dawn、Death Resolution、Day、Voting |
| 04. Game Services | 提供跨階段共用服務 | Win Condition、History、Timer、Player、Room |
| 05. Moderator | 提供系統上帝主持 | Narration Script、Moderator Runner、Voice Service |
| 06. Presentation & Platform | 顯示介面及提供裝置／連線能力 | Lobby、Seat、Role Panel、History UI、Media、Realtime、Persistence |

## 2.2 依賴方向

~~~text
Presentation / Platform
          |
          v
Application Orchestrator
          |
          v
Game Phases -----> Game Services
     |                    |
     v                    v
Game Core <---------- Role System
     |
     v
Game State / Event Contracts

Moderator Runner 接收流程事件並回報口白播放完成；
Moderator 不得自行改寫遊戲規則或決定遊戲階段。
~~~

實際專案可以依現有檔案載入方式調整，但不得違反以下邊界：

- Domain／遊戲規則模組不得依賴 DOM、window.alert、計時器、攝影機或麥克風 API。
- UI 模組不得直接修改玩家存活狀態、角色技能使用次數、勝負結果或目前階段。
- 角色資料庫不得執行技能或更改對局狀態。
- 主持腳本不得以口白播放順序取代遊戲狀態機。
- 平台模組不得自行決定狼人殺規則。
- 除 Game Core／指定狀態管理介面外，其他模組不得直接任意寫入共享狀態。

## 2.3 模組拆分粒度

模組應以「單一責任及穩定契約」拆分，而不是以每個按鈕、每個畫面或每個角色都建立一個獨立大型模組。

角色資料可集中管理；角色技能可按能力類型或觸發類型拆分。只有在角色行為具有獨立規則、測試需求或擴充價值時，才需要獨立的技能實作檔案。

# 3. 模組規格（Module Specifications）

本章定義目標模組。檔案名稱是建議的目標結構，不代表必須一次全部建立。

## 3.1 Game Core｜遊戲核心

### 3.1.1 Game State

**責任**
- 保存本局唯一權威狀態。
- 提供受控讀取與狀態更新入口。
- 管理玩家、角色、目前階段、回合數、房規、待結算結果及勝負狀態。
- 確保重開一局時，前一局的狀態不會殘留。

**不得**
- 直接操作畫面或播放口白。
- 把尚未公告的死亡結果當成已公開資訊。
- 讓不同模組各自保存互相矛盾的玩家存活狀態。

### 3.1.2 Phase Machine

**責任**
- 定義所有合法階段。
- 驗證階段轉換是否合法。
- 阻止未完成必要操作時提前轉換。
- 將自爆等中斷流程定義為明確、受驗證的特殊轉換。

**不得**
- 操作 DOM、計時器、語音或影音。
- 自行決定角色技能效果。
- 僅因某段口白播放完畢就假設遊戲階段可以轉換。

### 3.1.3 Command Handler

**責任**
- 接收玩家或系統提交的命令。
- 驗證命令者、所在階段、目標及權限。
- 呼叫對應領域模組。
- 回傳成功結果或可辨識的錯誤。

**不得**
- 信任 UI 傳入的合法性旗標。
- 讓未授權視角修改其他玩家的私密行動。
- 在驗證失敗時部分修改狀態。

### 3.1.4 Event Bus

**責任**
- 傳遞已發生的遊戲事件。
- 讓主持、紀錄及 UI 訂閱事件，而非互相直接呼叫內部函式。
- 保持事件順序可追蹤。

**要求**
- 事件名稱及 payload 必須有定義。
- 事件處理應可測試，避免重複執行造成重複死亡或重複公告。
- 公開事件與私密事件必須分流；不得把角色私密結果直接廣播給全場。

## 3.2 Role System｜角色系統

| 子模組 | 責任 | 不負責 |
|---|---|---|
| Role Registry | 登記標準角色、別名及角色能力註冊資訊 | 不執行對局技能 |
| Role Metadata | 陣營、分類、技能說明、時機、關係與版本差異 | 不變更玩家狀態 |
| Role Ability | 實作角色技能效果及觸發條件 | 不自行推進整局階段 |
| Action Validator | 驗證角色、目標、次數、階段及房規 | 不負責畫面呈現 |
| Visibility Policy | 決定玩家或觀眾可讀取哪些角色資訊 | 不決定技能結果 |

**角色新增要求**
- 先確認標準名稱與別名，不重複建立同一角色。
- 定義陣營、技能時機、合法目標、使用次數、衝突優先順序、死亡觸發及版本差異。
- 角色圖鑑資料與可遊玩技能實作必須分開標示。
- 只有 metadata 的角色不得被宣稱為技能已完成。
- 新技能必須有合法、非法、重複使用、目標已死亡、技能衝突及勝負影響測試。

詳見既有文件：docs/ADDING_ROLES.md。

## 3.3 Game Phases｜遊戲階段模組

| 模組 | 責任 | 完成條件 |
|---|---|---|
| Night Phase | 依本局角色與房規安排狼人及神職夜間行動 | 所有必要行動已提交或明確放棄 |
| Sheriff Election | 首夜警長競選、候選人、發言、投票及平票處理 | 選出唯一警長或正式結束為無警長 |
| Dawn Phase | 播報天亮並公布夜間基本死亡清單 | 公告完成，死亡清單與狀態一致 |
| Death Resolution | 依死因觸發獵人、狼王等死亡技能及連鎖 | 技能隊列清空，額外出局公告完成 |
| Sheriff Badge | 處理出局警長的警徽移交或銷毀 | 警徽狀態確定 |
| Day Speech | 管理白天發言順序及計時 | 所有應發言玩家完成或合法略過 |
| Public Voting | 管理公投、棄票、平票重投及處決 | 得出處決結果或無人出局 |
| Last Words | 管理遺言對象、時間及結束條件 | 遺言階段完成 |
| Self-Destruct | 驗證自爆者、階段及房規，並中斷當前白天流程 | 完成自爆效果及指定的下一階段 |

各階段可以使用共用服務，但不可以直接修改其他階段的私有內部資料。

## 3.4 Game Services｜共用遊戲服務

| 服務 | 唯一責任 |
|---|---|
| Win Condition Service | 依房規及正式遊戲狀態判定勝負 |
| History Service | 保存公開紀錄、私密紀錄及角色技能紀錄 |
| Timer Service | 管理倒數、暫停、取消及階段計時 |
| Player Service | 管理玩家座位、玩家識別及玩家狀態查詢 |
| Room Service | 管理房間、房主、座位及觀眾席 |
| Ruleset Service | 提供房規預設、覆寫及驗證 |

計時器到期不代表可以略過未完成的技能；計時器只負責通知階段模組，後續行為必須由該階段的規則決定。

## 3.5 Moderator｜上帝主持模組

| 子模組 | 責任 |
|---|---|
| Narration Script | 根據目前階段、角色及夜數產生口白內容 |
| Moderator Runner | 播放口白、等待語音結束、等待角色行動及推進主持呈現 |
| Voice Service | 封裝瀏覽器語音合成或未來語音供應商 |
| Moderator Event Handler | 接收階段事件並安排對應口白 |

**強制邊界**
- Game Flow 決定目前階段與下一階段。
- Moderator 只能提出「口白播放完成」或「播放失敗」等回報。
- 角色完成行動必須由命令驗證結果決定，不得只因 UI 點擊或口白播放完成就視為完成技能。
- 私密資訊不得透過公開語音或全場公告洩漏。
- 語音 API 不可用時，仍須維持相同的規則與階段閘門。

詳見既有文件：docs/MODERATOR_SCRIPT.md、docs/MODERATOR_ACTION_GATING.md。

## 3.6 Presentation & Platform｜介面與平台

### UI 子模組
- Lobby UI：首頁、建立房間、加入房間。
- Seat UI：座位、玩家資訊及影音容器。
- Role Panel UI：目前視角玩家的操作控制台。
- Night UI：夜間角色操作畫面。
- Sheriff UI：警長競選與投票介面。
- Dawn／Death UI：天亮公告、出局名單及死亡技能操作提示。
- Day／Voting UI：白天發言、公投、平票及遺言。
- History UI：全局紀錄與角色私密紀錄。
- Settings UI：房規、媒體及其他設定。
- Compendium UI：角色圖鑑與搜尋。

UI 只能顯示領域模組提供的資料，並提交命令；不得自己判定存活、勝負或技能結果。

### Platform 子模組
- Media Adapter：攝影機、麥克風及本機媒體串流。
- Realtime Adapter：未來多人連線與訊令通道。
- Persistence Adapter：未來房間與遊戲狀態儲存。
- Identity／Permission Adapter：未來玩家驗證與操作權限。

目前的房間加入及影音能力仍屬本機原型範圍。Realtime、伺服器權威狀態、斷線重連、遠端 WebRTC 與正式權限系統不得標記為已完成，除非有對應程式、測試與驗收證據。

# 4. Game State Specification｜遊戲狀態規格

## 4.1 狀態所有權

| 資料 | 主要管理者 | 其他模組的使用方式 |
|---|---|---|
| currentPhase | Phase Machine | 讀取，不得自行改寫 |
| currentDay | Game Core／Round Manager | 讀取；由正式回合轉換更新 |
| players | Game State／Player Service | 透過命令及領域操作更新 |
| role／team | Role System + Game State | 依角色註冊資料查詢 |
| lifeState／isAlive | Game State + Death Resolution | 讀取；只透過正式死亡／復活操作變更 |
| pendingNightDeaths | Night Phase／Game State | Dawn 與 Death Resolution 讀取 |
| deathSkillQueue | Death Resolution | 其他模組不得直接增刪 |
| sheriffCandidates／sheriffVotes | Sheriff Election | UI 只能提交候選與投票命令 |
| sheriffId／badgeState | Sheriff Election／Sheriff Badge | 依模組命令更新 |
| ruleset | Ruleset Service | 讀取；開局後依規則限制是否可變更 |
| gameHistory | History Service | 透過紀錄事件寫入 |
| winner／gameOver | Win Condition Service／Game Core | 其他模組不得自行宣告勝利 |

若同一欄位在多個模組被直接寫入，視為架構缺陷。

## 4.2 玩家生命狀態與待公布死亡

**MUST：待公布死亡不能靠切換 isAlive 來隱藏。**

目標資料模型應明確區分：

~~~js
{
  playerId: 5,
  lifeState: "PENDING_DEATH", // ALIVE | PENDING_DEATH | DEAD
  deathReason: "KILLED_BY_WOLF"
}
~~~

夜間死亡待公布資料應保存為獨立清單：

~~~js
{
  pendingNightDeaths: [
    {
      playerId: 5,
      cause: "KILLED_BY_WOLF",
      source: "WOLF",
      night: 1,
      announced: false
    }
  ]
}
~~~

上方僅為目標資料結構示意，不是目前 main 分支已採用的 schema。

要求：

1. PENDING_DEATH 是系統內部狀態，不等於已對玩家公開的「已出局」。
2. 在天亮公告前，第一人稱控制面板及其他不應揭露死訊的公開區域不得顯示「已出局」或提前暴露死亡原因。
3. 不得把待公布死亡者暫時改回存活，以便讓 UI 或競選流程運作。
4. 參選、投票及其他階段資格必須由獨立 eligibility policy 判斷，不得只靠 UI 顯示文字或直接假設 PENDING_DEATH 一定可參與／不可參與。
5. Dawn 公告時才執行正式死亡狀態轉換，並建立不可重複的公開結果。
6. 死亡原因應保留，供死亡技能資格、紀錄與勝負判定使用。
7. 同一玩家同一夜產生多個死亡來源時，必須有明確的死因合併／優先規則，不能重複公告同一座位。

**遷移注意：** 目前 Game Engine 的夜晚結算會直接更新玩家的 isAlive；PR #35 曾以暫時恢復存活狀態處理首夜警長競選。這是目前應優先整理的狀態邊界，不代表目標規格允許此做法。

## 4.3 死亡資料分類

死亡資料至少區分：

- **Night Base Deaths：** 夜間基本死亡結果，包括已確認的狼人襲擊、女巫毒藥及夜間獵人開槍等死亡來源。
- **Death-Skill Chain Deaths：** 天亮公布後，因獵人、狼王或其他死亡技能造成的額外死亡。
- **Public Execution Deaths：** 白天投票處決造成的死亡。
- **Self-Destruct Deaths：** 小狼或其他符合房規角色自爆造成的死亡。

不得將「狼人選定的夜刀目標」直接等同於死亡；必須等待守衛、女巫及其他房規完成結算後，得到確認死亡的結果。

## 4.4 狀態更新一致性

- 一個命令要嘛完整成功，要嘛不留下部分變更。
- 同一命令不得因語音重播、UI 重繪或重複事件而重複執行。
- 新局必須清除上一局的待結算死亡、技能隊列、計時器、投票及主持狀態。
- 所有跨模組狀態變更必須可追溯其觸發命令或事件。

# 5. Phase State Machine｜遊戲階段狀態機

## 5.1 階段設計原則

階段狀態機是遊戲流程的唯一權威。每個階段必須定義：

- 進入條件（Entry Conditions）
- 可接受命令（Allowed Commands）
- 完成條件（Completion Conditions）
- 超時行為（Timeout Policy）
- 合法下一階段（Allowed Transitions）
- 結束後事件（Exit Events）

現有 js/game-flow.js 已有基本階段轉換表，但它不是完整的遊戲流程編排器；後續應將「合法轉換」與「階段內行為」分開。

## 5.2 第一夜警長競選的已確認流程

**這個順序是 Awoo 的明確玩法要求，不得自行改成其他順序：**

~~~text
夜間行動
（所有狼人與神職必要行動全部完成）
        |
        v
上帝口白：
「天將破曉，競選警長的人請舉手……」
        |
        v
警長競選階段完整結束
（舉手／退出、候選人發言、投票及必要的平票處理）
        |
        v
上帝口白：
「天亮請睜眼」
        |
        v
公布昨夜已確認出局名單
        |
        v
處理因夜間死亡而觸發的死亡技能
        |
        v
處理警徽及後續白天流程
~~~

強制規則：

1. 所有夜間狼人及神職行動完成後，才可以開始警長競選入口口白。
2. 第一夜若啟用警長競選且尚未選出警長，必須先完整執行警長競選。
3. 警長競選尚未完成時，不得播放「天亮請睜眼」或公布昨夜死亡名單。
4. 警長競選期間，第一人稱控制面板不得提前顯示「已出局」；公開紀錄也不得提前揭露夜間死亡結果。
5. 競選資格必須使用明確的規則判斷，不能由 UI 是否顯示「已出局」決定。
6. 競選結束後，才播放「天亮請睜眼」，接著公布昨夜死亡結果。
7. 若本局不啟用警長競選，或不是需要首夜選警長的情境，則依正式流程直接進入天亮階段。
8. 警長競選無候選人、無有效票、平票重投後仍平票等情況，都必須有明確結束結果，且不得卡住天亮流程。

## 5.3 後續夜晚的基本流程

已經有警長或當晚不需要進行首夜競選時：

~~~text
夜間行動完成
      |
      v
「天亮請睜眼」
      |
      v
公布昨夜基本死亡名單
      |
      v
死亡技能連鎖
      |
      v
警徽處理（如有需要）
      |
      v
白天發言
~~~

## 5.4 天亮死亡公告與技能連鎖

天亮前必須先完成夜晚所有基本死亡結果的統計。至少包含：

- 狼人襲擊，且經守衛／女巫等房規結算後確認死亡者。
- 女巫毒藥造成的死亡者。
- 夜間獵人開槍造成的死亡者。
- 其他已實作且屬於夜間結算的死亡效果。

天亮時一次公布這一批基本死亡座號，不得漏號、重複或提前透露死因。

例：若夜間獵人開槍帶走狼王，狼王必須在天亮公布自己出局後，才進入狼王死亡技能流程。若狼王技能再帶走其他玩家，該額外死亡應在對應技能鏈及必要遺言完成後，依公告規則公布。

死亡技能連鎖要求：

1. 基本死亡清單先定案並公告。
2. 依死亡原因及角色能力建立技能隊列。
3. 每個技能行動都必須通過合法角色、狀態、目標及使用次數驗證。
4. 技能造成的新死亡加入連鎖隊列；可觸發的後續技能依規則繼續處理。
5. 連鎖結束後，依角色及房規完成遺言／額外死亡公告。
6. 勝負判定必須在所有可能改變存活數及勝負的必要死亡技能結算完成後執行。
7. 不得因第一個死亡事件暫時達成勝負條件，就跳過仍可改變結果的死亡技能。

## 5.5 目標階段清單

以下是目標階段概念；重構時可與現有 phase ID 做相容映射，不要求一次改名：

| 目標階段 ID | 用途 |
|---|---|
| LOBBY | 大廳／開局前 |
| NIGHT | 狼人及神職夜間行動 |
| PRE_DAWN_ANNOUNCEMENT | 「天將破曉」及警長競選入口口白 |
| SHERIFF_ELECTION | 競選舉手、候選人與發言 |
| SHERIFF_VOTING | 警長投票及平票處理 |
| DAWN_ANNOUNCEMENT | 「天亮請睜眼」 |
| NIGHT_DEATH_REVEAL | 公布夜間基本死亡結果 |
| DEATH_SKILL_RESOLUTION | 獵人、狼王等死亡技能及連鎖 |
| SHERIFF_BADGE | 警徽移交或銷毀 |
| DAY_SPEECH | 白天發言 |
| VOTING | 公投、平票重投及處決 |
| LAST_WORDS | 遺言 |
| GAME_OVER | 終局 |

若角色死亡技能、警徽或遺言流程的先後受房規影響，必須由明確流程政策決定，不得散落在多個 UI handler 中。

## 5.6 其他流程分支

- **警長投票平票：** 依規則進行限定候選人的重投；達到重投上限仍無唯一結果時，以無警長結束競選。
- **白天公投平票：** 依既有玩法規格進入平票候選人發言與重投；重投後仍平票時不得任意處決。
- **白天自爆：** 只有符合角色、房規與階段條件的命令才能中斷當前白天流程並入夜。
- **白狼王自爆帶人：** 必須先完成自爆驗證與目標選擇，再執行其規定的出局及入夜流程。
- **警長出局：** 進入警徽移交／銷毀流程；處理後回到原本等待的流程，不可重複觸發天亮或遺言。
- **無警長：** 白天發言起始座位由 Day Speech 模組決定；不能因缺少警長而阻斷日間流程。
- **遊戲結束：** 必須清除計時器與待執行主持工作，且不得再接受一般遊戲命令。

# 6. Command & Event Contracts｜命令與事件契約

## 6.1 命令（Commands）

命令代表「有人要求系統做一件事」，必須經驗證才可成功。

| 命令 | 主要處理模組 | 必要驗證 |
|---|---|---|
| SubmitNightAction | Night Phase／Role Action | 玩家身分、角色、階段、目標、次數、房規 |
| PassNightAction | Night Phase | 該角色可否放棄該技能及是否已提交 |
| JoinSheriffElection | Sheriff Election | 目前階段、玩家資格、候選狀態 |
| WithdrawSheriffCandidate | Sheriff Election | 候選人是否仍可退出 |
| CastSheriffVote | Sheriff Election | 投票者資格、候選人有效、不可重複投票 |
| CompleteSheriffElection | Sheriff Election | 候選人／投票／平票條件是否已完成 |
| RevealNightDeaths | Dawn Phase | 夜間結果已結算、公告未重複執行 |
| ResolveDeathSkill | Death Resolution | 技能者、死因、目標、使用次數及技能隊列 |
| CastPublicVote | Public Voting | 玩家資格、投票階段、有效目標及不可重複投票 |
| ResolveSheriffBadge | Sheriff Badge | 警長狀態、目標存活及移交／銷毀選項 |
| UseSelfDestruct | Self-Destruct | 角色、房規、階段、目標與中斷條件 |

命令名稱可隨實作調整，但其責任及驗證要求不得消失。

## 6.2 事件（Events）

事件代表「某件已驗證的事實已經發生」。

| 事件 | 產生時機 | 主要訂閱者 |
|---|---|---|
| NightActionsCompleted | 夜間必要行動全部完成 | Phase Coordinator、Moderator |
| SheriffElectionStarted | 進入警長競選 | Sheriff UI、Moderator、Timer |
| SheriffElectionCompleted | 選出警長或無警長 | Phase Coordinator、History |
| DawnAnnouncementStarted | 開始天亮口白 | Moderator、Dawn UI |
| NightDeathsRevealed | 基本死亡清單正式公布 | Death Resolution、History、UI |
| DeathSkillTriggered | 某死亡者符合技能資格 | Death Resolution、Moderator、Role Panel |
| DeathSkillResolved | 技能完成或放棄 | Death Resolution、History |
| AdditionalDeathsRevealed | 技能連鎖的額外死亡正式公布 | UI、History、Win Condition |
| DayPhaseStarted | 死亡及警徽必要流程完成 | Day Speech、Moderator |
| VoteResolved | 公投結果確定 | Death Resolution、History |
| GameEnded | 勝負條件正式成立 | UI、History、Room Service |

## 6.3 事件資料與隱私

- 公開事件只包含全體玩家可知的資訊。
- 私密事件必須帶有接收者或角色視角範圍。
- 不得把女巫狼刀資訊、預言家查驗結果或其他私密資訊放進公開事件 payload。
- Event Handler 必須考慮重複事件；死亡公告及技能效果不得因重播或重新渲染而執行第二次。

# 7. Module Contract｜模組契約格式

每個新模組或被拆出的舊模組，必須在設計文件中填寫以下項目：

| 欄位 | 必填內容 |
|---|---|
| Module ID | 穩定且唯一的模組識別名稱 |
| Purpose | 唯一主要責任 |
| Owns | 唯一擁有／可寫入的狀態 |
| Reads | 可讀取的外部狀態 |
| Commands | 可接受的命令 |
| Emits | 成功後發出的事件 |
| Consumes | 會訂閱的事件 |
| Dependencies | 可依賴的模組或介面 |
| Must Not | 明確禁止事項 |
| Errors | 驗證錯誤、狀態衝突、重複提交與恢復策略 |
| Tests | 單元、整合、流程及回歸案例 |

模組函式應使用明確輸入與結果，不應依賴隱藏的全域變數或直接讀取 DOM。

建議統一結果格式：

~~~js
{
  ok: true,
  data: {},
  events: []
}

// 失敗時
{
  ok: false,
  error: {
    code: "INVALID_PHASE",
    message: "目前階段不能執行此操作。"
  }
}
~~~

以上是介面概念，不是要求所有舊函式現在立即改寫。遷移時可先用 Adapter 包裝舊函式，再逐步收斂。

# 8. Role Ability Contract｜角色技能契約

每一個可遊玩技能至少要定義：

1. 技能識別碼與所屬角色。
2. 觸發時機：夜間主動、白天主動、出局觸發、被動或持續效果。
3. 角色必須存活或已出局的條件。
4. 目標類型與合法目標條件。
5. 使用次數及消耗時機。
6. 是否可放棄。
7. 作用結果與死亡原因。
8. 與其他技能同時發生時的結算優先序。
9. 是否會觸發其他死亡技能。
10. 對勝負判定、紀錄及資訊可見性的影響。
11. 房規差異及角色版本差異。
12. 單元測試與完整流程測試。

角色技能不得直接操作 UI、語音、計時器或房間網路。技能回傳結果，由所屬階段模組負責套用結果與推進流程。

# 9. UI、Moderator 與權限規格

## 9.1 UI

- UI 只呈現資料與收集操作。
- 所有會改變遊戲狀態的操作，必須提交 Command。
- UI 不得以自己顯示的數字或按鈕可用狀態作為權限驗證。
- 視角切換只允許在本機測試模式，不能作為未來多人正式版的權限機制。
- 公開畫面、角色面板及觀眾視角必須使用一致的 Visibility Policy。

## 9.2 上帝主持

- 主持口白應綁定階段事件或流程提示。
- 有角色行動的口白，必須等待合法行動完成或明確放棄。
- 語音播放完畢不是技能完成的證據。
- 語音失敗時，系統仍須保持同樣的行動驗證與階段順序。
- 主持流程不得在警長競選完成前播報「天亮請睜眼」或昨夜出局名單。

## 9.3 未來多人權限

多人版必須採伺服器權威（Server-authoritative）狀態：

- 客戶端只能提交命令，不能自行決定投票、技能結果或玩家存活狀態。
- 伺服器驗證玩家身分、房間成員、角色權限及目前階段。
- 私密角色資訊只能傳給授權客戶端。
- 重新連線後由伺服器狀態恢復，不以客戶端舊狀態覆蓋伺服器。
- 視訊／音訊的媒體傳輸與遊戲規則狀態分離。

目前專案尚非真正多人連線版；這些是未來規格，不是現況聲明。

# 10. Testing & Quality Standards｜測試與品質標準

## 10.1 測試層級

| 層級 | 目的 | 例子 |
|---|---|---|
| Unit | 驗證單一規則或純函式 | 夜間合法目標、毒藥限制、技能資格 |
| Module Integration | 驗證兩個以上模組的契約 | 夜晚結算結果送入死亡技能模組 |
| Flow Integration | 驗證完整階段順序 | 夜間 → 警長競選 → 天亮 → 出局公告 |
| Regression | 保護已修好的既有行為 | 警長競選平票、警徽移交、狼王連鎖 |
| UI／Browser | 驗證真實瀏覽器操作與顯示 | 第一人稱控制面板不提前顯示已出局 |
| Device Acceptance | 驗證不同裝置及權限 | 手機 Safari／Chrome、攝影機與麥克風權限 |
| Multiplayer Acceptance | 驗證多人同步與權限 | 多瀏覽器同時投票、斷線重連、私密資訊隔離 |

## 10.2 必須具備的流程回歸測試

以下情境是 Awoo 核心流程的最低保護範圍：

- 第一夜夜間行動完成後，先播放「天將破曉，競選警長的人請舉手」。
- 警長競選完整結束之前，不得進入天亮公告。
- 首夜警長競選期間，第一人稱控制面板不得提前顯示「已出局」。
- 警長競選結束後，先播放「天亮請睜眼」，再公布昨夜出局座號。
- 狼刀、女巫毒藥與夜間獵人開槍造成的基本死亡，必須全部進入同一批天亮公告。
- 獵人夜間開槍帶走狼王時，天亮公布狼王出局後，狼王可以發動死亡技能。
- 死亡技能造成的額外死亡要加入連鎖及紀錄，不得漏號或重複。
- 死亡技能連鎖結束後才執行必要的勝負判定。
- 警長出局時，警徽移交／銷毀能正確回到原本流程。
- 女巫首夜藥劑限制、後續夜晚規則及毒藥實際死亡結果。
- 公投平票、警長投票平票、自爆中斷白天及遺言流程。
- 重開新局後不保留前一局的技能使用、死亡、計時及投票資料。

## 10.3 CI 與人工驗收的差異

- CI 通過代表被自動化測試覆蓋的檢查通過。
- 靜態 HTML／CSS 測試不等同畫面實際可用。
- Node.js 單元測試不等同瀏覽器端到端測試。
- 瀏覽器測試不等同手機實機與多人測試。
- 每個 PR 必須清楚記錄實際執行的測試及尚未驗收的項目。

任何 PR 不得使用「全部修好」描述只通過語法或局部單元測試的功能。

- 對警長競選、夜間死亡、天亮公告、死亡技能建立完整流程測試案例。
- 先確認目前可重現的 Bug，不用重構掩蓋未理解的問題。

完成條件：
- 有可重現的測試基線。
- 已完成／部分完成／未完成狀態均有證據。
- 沒有未記錄的高風險流程被直接搬移。

## Phase 1 — Game State & Phase Machine

**目標：** 建立單一狀態來源與可靠階段轉換。

工作：
- 定義狀態 schema 與資料所有權。
- 分離 pending death 與正式 dead 狀態。
- 明確定義第一夜警長競選與天亮的階段順序。
- 將階段轉換與階段執行責任分離。

完成條件：
- 不再透過切換 isAlive 來隱藏或恢復待公布死亡。
- 階段轉換有明確測試。
- 舊版 UI 可透過 Adapter 讀取新狀態，不必一次全面改寫。

## Phase 2 — Night & Sheriff Election

**目標：** 分離夜間行動與警長競選。

工作：
- 將夜間行動提交、完成判斷與夜間結算分開。
- 將警長候選、退出、發言、投票、平票與結束條件獨立化。
- 讓警長競選完成事件成為進入天亮的唯一入口之一。

完成條件：
- 完整通過第一夜順序及警長競選測試。
- 不破壞既有候選人退出及平票流程。
- 第一人稱控制面板不提前揭露待公布死亡。

## Phase 3 — Dawn & Death Resolution

**目標：** 將基本死亡公告與死亡技能連鎖分開。

工作：
- 夜間死亡結果建立 pending death 清單。
- 天亮公告統一公布基本死亡。
- 死亡技能模組依死因建立技能隊列。
- 連鎖死亡及必要遺言完成後，再處理額外公告與勝負判定。

完成條件：
- 狼刀、女巫毒藥、夜間獵人開槍均可正確進入基本死亡清單。
- 獵人帶走狼王的連鎖流程正確。
- 無重複死亡、漏公告或提早結束遊戲。

## Phase 4 — Day, Voting & Sheriff Badge

**目標：** 拆分白天發言、公投、遺言與警徽處理。

完成條件：
- 平票、重投、處決、死亡技能、警徽處理及遺言的交接均有流程測試。
- 白天自爆可依房規合法中斷流程。
- 遊戲結束後所有計時器及待處理工作均已清理。

## Phase 5 — Moderator & Shared Services

**目標：** 將主持、語音、歷史紀錄及計時器從主控制器抽離。

完成條件：
- 主持模組不再決定遊戲規則或自行改變階段。
- 語音失敗不會使遊戲流程卡死。
- 計時器不會略過必要的角色操作。

## Phase 6 — UI & Platform Separation

**目標：** 讓 UI、影音與未來多人連線使用相同的遊戲核心契約。

完成條件：
- UI 只呈現狀態並提交命令。
- Media Adapter 不擁有遊戲規則。
- 多人版可將 Command Handler／Game State 放到伺服器端，而不必重寫遊戲規則核心。

## 12.1 每次遷移的安全規則

1. 一個 PR 原則上只移轉一個主要責任範圍。
2. 搬移前先寫測試或補齊現有測試。
3. 不在同一個 PR 順便改動無關玩法或 UI。
4. 不得同時存在兩份互相獨立的權威狀態。
5. 新舊實作並存時，必須有明確 Adapter 與移除條件。
6. PR 必須列出變更檔案、行為差異、測試結果、人工驗收及未完成項目。
7. 未經使用者確認的遊戲規則，不得以重構名義變更。

# 13. Versioning & Change Management｜版本與變更管理

## 13.1 產品版本與規格版本分開

- **產品版本：** 遵守專案版本號規範，例如目前產品版本基準 0.9.4-alpha.1。
- **架構規格版本：** 本文件獨立使用 1.0.0；只在架構規格本身有變更時遞增。
- 文件版本不會自動改變產品 package.json 版本。
- 純文件提交若沒有改變產品程式行為，不應假裝是一個新的遊戲功能版本；但仍須依專案要求更新 CHANGELOG。

## 13.2 產品 SemVer 原則

依專案提供的《狼人殺網頁遊戲項目：版本號規範與架構管理指南》：

- X：主版本號，重大架構或不向下相容變更。
- Y：次版本號，新增角色、新流程或向下相容的新功能。
- Z：修訂號，Bug 修復及邏輯微調。
- alpha.N：內部開發測試。
- beta.N：公開／壓力測試。

每次提交或打包發布，CHANGELOG.md 應用一句話記錄調整內容；前後端版本需保持可追溯與相容。

**待確認的版本規則歧義：** 提供的指南一方面把「不向下相容的 API／WebSocket 變更」列為主版本遞增，另一方面又把 JSON 通訊欄位變更描述為直接提升次版本號。兩者可能衝突。正式多人協定開始前，必須決議「新增欄位」與「移除／改變既有欄位」的版本遞增方式，不能由開發者自行猜測。

## 13.3 變更流程

1. 提出需求與預期行為。
2. 確認是否屬於既有模組責任，還是需要新增模組。
3. 檢查對狀態 schema、階段轉換、命令及事件的影響。
4. 更新規格或對應模組文件。
5. 補上測試。
6. 建立獨立分支及 PR。
7. 取得 CI 結果及必要人工驗收。
8. 合併後更新 CHANGELOG，並確認部署狀態。

# 15. Open Decisions｜待決議事項

以下事項在正式實作前需要明確決議；規格不應用猜測填補：

1. **首夜待公布死亡者的警長競選資格：** UI 不得提前顯示「已出局」已確認；但是否可以舉手、成為候選人或投票，必須由明確房規決定，不能與資訊顯示混為一談。
2. **死亡技能與警徽處理的優先序：** 當同一晚同時有多個死亡技能及警長出局時，需定義唯一的技能隊列與警徽交接順序。
3. **同一目標受到多個死亡來源：** 需定義死亡原因合併、技能資格與公開紀錄的優先規則。
4. **死亡技能遺言規則：** 哪些角色需要遺言、先後順序及逾時處理需逐角色／房規明確化。
5. **多人協定版本：** 在選定後端及通訊協定前，先完成版本號歧義決議。
6. **重構模組命名與目錄：** 本文件的目標目錄可在 Phase 0 盤點後微調，但模組責任與依賴原則不應被削弱。

# 16. Acceptance Checklist｜架構驗收清單

架構重構達到可接受狀態前，必須能回答「是」：

- [ ] 每個核心狀態都有唯一的管理者。
- [ ] UI 不會直接改寫遊戲規則。
- [ ] Phase Machine 控制所有合法階段轉換。
- [ ] 主持口白和遊戲流程已分離。
- [ ] 角色 metadata 和可執行技能已分離。
- [ ] 夜間死亡與正式公開出局已分離。
- [ ] 第一夜完整遵循「夜間行動 → 天將破曉 → 警長競選完成 → 天亮請睜眼 → 公布昨夜出局」。
- [ ] 夜間基本死亡會完整彙整，死亡技能連鎖不會漏算。
- [ ] 勝負判定不會搶在必要死亡技能前執行。
- [ ] 警徽、平票、自爆、遺言等流程有明確交接。
- [ ] 主要模組都有契約及測試。
- [ ] app.js 已逐步縮減為應用程式協調入口，而不是所有規則的集中地。
- [ ] 自動化測試、瀏覽器驗收及多人驗收被清楚區分。
- [ ] 未來多人版可以把權威狀態移至伺服器，而不必重寫遊戲規則核心。
