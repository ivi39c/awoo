## 1. 稽核範圍與限制

本文件是 Phase 0 的 source-level audit，目的是確認目前程式實際做到什麼、測試證明什麼，以及需求和現況的差距。

本次沒有在本機 checkout 執行 `npm run check`，也沒有啟動瀏覽器或實際操作手機。因此：
- 測試數量是依目前 `tests/*.test.cjs` 各檔案的測試宣告盤點。
- GitHub Actions 狀態只代表該 workflow 中的 Node.js 語法檢查與自動化測試，不代表完整瀏覽器、手機或多人端到端驗收。
- 程式碼行數與呼叫次數是靜態掃描的約略指標，不是完整 AST 複雜度分析。
- 「程式有實作」不等於「符合產品需求」；若程式路徑與已確認規則衝突，以需求規格為驗收基準。

## 3. 核心流程稽核

### 3.1 夜間角色順序

**狀態：符合目前已確認順序；文件需同步。**

目前 `ruleset.js` 預設使用 `classic`，`moderator-script.js` 的實際排序對應守衛 → 狼人 → 女巫 → 預言家；`tests/moderator-script.test.cjs` 也有測試守衛先於狼人、狼人先於女巫、女巫先於預言家。

但 `docs/MODERATOR_SCRIPT.md`、README 與較早的 handoff／traceability 文件仍保留舊的狼人在先或「尚待協調」敘述。文件彼此不一致，容易讓後續開發工具採用錯誤規則。需在文件整理階段統一。

### 3.2 首夜警長競選順序

**高優先級：目前與已確認需求衝突**

**已確認的需求順序：**

1. 所有夜間角色與狼人行動完成。
2. 上帝說：「天將破曉，競選警長的人請舉手……」
3. 完整結束警長競選：舉手、退出、候選人發言、投票，以及必要的平票／無警長處理。
4. 上帝說：「天亮請睜眼」。
5. 公布昨夜實際出局名單。
6. 依死亡技能資格處理獵人、狼王等連鎖，再檢查勝負。

**目前程式實際順序：**

`moderator-script.js` 在夜間主持腳本最後固定加入「天亮請睜眼。」（約第 500 行）。`app.js` 的 `advanceModeratorLine()` 在該最後一句播完後呼叫 `resolveNightNow()`。若首夜警長模式啟用，`resolveNightNow()` 才進入 `SHERIFF_ELECTION` 並呼叫 `startSheriffCountdown()`。

所以目前首夜會先播「天亮請睜眼」，再播「天將破曉，請競選警長的玩家舉手」並進行警長競選；警長當選或無警長後，`announceDayDeath()` 播的是「天亮了。昨夜……」，而不是把「天亮請睜眼」放在競選結束後。

**結論：流程順序相反，必須修正。** 現有 `tests/moderator-script.test.cjs` 只驗證「天亮請睜眼」是夜間腳本最後一句，沒有把它與警長競選階段整合測試，因此目前測試會接受這個錯誤順序。

### 3.3 警長候選人發言

**尚未完成**

目前 `candidateSheriff()` 支援舉手／退出；`processSheriffCandidates()` 在倒數結束後，無候選人則進入無警長，有一位候選人則直接當選，多位候選人則直接進入 `SHERIFF_VOTING`。

`startSheriffVoting()` 的口白寫著「警長候選人發言結束」，但目前查到的流程沒有逐位候選人發言階段、候選人發言隊列或對應計時器。也沒有警長競選整合測試驗證候選人發言、退出、投票與平票重投的完整順序。

**結論：目前有候選登記及投票雛形，不可標記為完整警長競選。**

### 3.4 首夜待公布死亡狀態

**高優先級：狀態模型與目標架構衝突**

目前 `game-engine.js` 的 `resolveNight()` 會直接將夜間死亡者的 `isAlive` 設為 `false`。首夜有警長競選時，`app.js` 的 `resolveNightNow()` 又把這些玩家的 `isAlive` 改回 `true`，並設定 `firstNightDeathsHiddenUntilDawn`；`announceDayDeath()` 才再次將他們設為 `false`。

這是暫時復活以維持競選流程，不是獨立的待公布死亡狀態。它會讓候選資格、投票資格、目標是否合法等規則，在競選期間自動把這些玩家當作存活者。

目前 `candidateSheriff()`、`voteSheriff()` 及警長投票面板主要依賴 `player.isAlive`，沒有獨立 eligibility policy。

**已知尚待產品決策：** 首夜待公布死亡者是否可以舉手參選、成為候選人、參與警長投票？目前程式的實際效果是允許，因為它把待公布死亡者暫時設回存活。這只是現況，不代表已獲得產品確認。

**目標修正方向：** 將生命狀態與公開可見性分離，例如 `ALIVE / PENDING_DEATH / DEAD`，並以明確的 eligibility policy 判斷候選與投票資格。不得以暫時切換 `isAlive` 隱藏死訊。

### 3.5 夜間死亡公告與死亡技能連鎖

**狀態：部分實作，整合驗收不足。**

目前夜間結算會彙整狼人襲擊、女巫毒藥及夜間獵人開槍的死亡座號；公開歷史暫存至天亮公告後才寫入。獵人與狼王有死亡技能資格判定，`app.js` 也有死亡技能佇列與追加連鎖的處理。

現有引擎測試涵蓋死亡技能資格、目標存活檢查及部分連鎖勝負判定；但目前沒有完整整合測試證明「首夜警長競選 → 天亮公告 → 多名死亡技能角色 → 技能連鎖 → 警徽處理 → 勝負檢查」全程正確。

目前程式在天亮後先處理死亡技能佇列，再進入 `continueDayAfterDawn()` 判定勝負與警徽處理。這是現有實作順序；死亡技能與警徽的優先權仍應列為產品規則決策，並用測試固定。

### 3.6 警長票選與警徽

| 功能 | 程式現況 | 測試現況 |
|---|---|---|
| 候選人舉手／退出 | 有 | 無完整整合測試 |
| 單一候選人直接當選 | 有 | 無完整整合測試 |
| 多候選人投票 | 有 | 無完整整合測試 |
| 第一輪平票後重投 | 有 | 無完整整合測試 |
| 第二輪仍平票／無有效票 | 會進入無警長 | 無完整整合測試 |
| 警長死亡移交／銷毀警徽 | 有 `SHERIFF_BADGE` 流程 | 主要只有階段轉換等間接測試，缺少完整行為測試 |

因此警長功能應標記為「部分接入、尚未端到端驗收」，不能只因為有對應函式與 UI 就標記為完成。

## 7. Phase 1 建議順序（本次不執行）

Phase 0 完成後，建議依序推進；每個階段都必須先有驗收測試，再改動相應程式：

1. **先修正首夜流程規格與測試護欄**：測試必須驗證夜間口白、警長競選、天亮口白、死訊、死亡技能與勝負檢查的時間順序。
2. **建立生命狀態與 eligibility policy**：移除暫時把死亡者設回存活的做法；DEC-01 必須先有產品答案。
3. **補齊警長競選流程**：候選人發言、投票、平票重投、無警長與警徽處理皆有整合測試。
4. **補齊夜間死亡與死亡技能整合測試**：涵蓋多種死亡來源、獵人／狼王連鎖、警徽處理及勝負檢查。
5. **才開始拆分 `app.js`**：每次只抽出一個責任，不同 PR 不同職責；先保留現有行為，再逐步收斂狀態來源。
6. **多人連線與 WebRTC 獨立規劃**：必須先定義伺服器權威狀態與玩家權限，不能將目前本機原型描述為多人已完成。
